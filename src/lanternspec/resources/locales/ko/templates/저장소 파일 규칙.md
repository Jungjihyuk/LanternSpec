# 📘 저장소 파일 규칙

> [!abstract] 한눈에 보기
> `.gitignore` · `docker-compose.yml` · README · CHANGELOG · LICENSE · 폴더 구조를 **처음 만들 때** 따르는 형식입니다.
> 처음 만든 형식이 이후 변경의 기준이 되므로, 처음부터 읽기 쉽게 만듭니다.
> 이미 있는 파일은 그 파일의 형식을 지키고, 새 항목은 맞는 묶음에 넣습니다.

## 공통 주석 원칙
- **머리 블록:** 파일 맨 위에 무엇을 하는 파일인지, 어떤 기준으로 나눴는지, 자주 쓰는 명령을 적습니다.
- **큰 묶음:** 번호를 붙이고 구분선으로 나눕니다. 순서는 머리 블록에 적은 기준을 따릅니다.
- **소묶음:** 큰 묶음 안에서 `##` 한 줄 제목으로 나눕니다.
- **이유 주석:** 값이 왜 그런지 바로 알기 어려운 줄에는 줄 끝에 이유를 적습니다. 무엇인지는 이름으로 드러나므로 적지 않습니다.
- **새 항목:** 맨 아래에 붙이지 않고 맞는 묶음에 넣습니다. 맞는 묶음이 없으면 새 묶음을 만들고 머리 블록에도 더합니다.

## .gitignore
분류 기준은 **"누가 · 무엇이 만드는가"**입니다. 프로젝트에 없는 묶음은 뺍니다.

```gitignore
# ============================================================
# .gitignore 분류 기준: "누가/무엇이 생성하는가"
# ============================================================
# 1. Environment   — 개발 환경이 생성 (OS, 편집기, 로그)
# 2. Build         — 빌드 산출물
# 3. Toolchain     — 언어 도구가 생성 (가상 환경, 캐시)
# 4. Data          — DB · 데이터 파일
# 5. AI Tools      — AI 도구가 생성 (설정을 커밋하지 않는 경우만)
# 6. Infra         — 환경 변수, 비밀, 배포 관련
# 7. Documentation — 내부 문서, 초안
# ============================================================


# ========================= 1. Environment ===========================

## OS - macOS
.DS_Store

## IDE / Editor
.idea/
.vscode/

## Logs
*.log


# ========================= 3. Toolchain =============================

## Python
__pycache__/
.venv/


# ========================= 6. Infra =================================

## Environment Variables
.env
.env.*.local    # .env.example은 커밋한다 (필요한 값의 목록)
```

## docker-compose.yml
```yaml
# =============================================================================
# <프로젝트> 개발용 Docker Compose
#
# 서비스 구성:
#   db        - PostgreSQL (개발 DB · 테스트 DB)
#   backend   - API 서버
#   frontend  - 웹 화면 개발 서버
#
# 처음 한 번: cp .env.example .env
# 실행:       docker compose up -d
# 자주 쓰는 명령: (마이그레이션 · 테스트 계정 · 테스트)
# =============================================================================

# 어느 폴더(worktree)에서 띄워도 같은 컨테이너 · 볼륨을 쓰도록 이름을 고정한다
name: <프로젝트>

services:
  # ---------------------------------------------------------------------------
  # DB - PostgreSQL
  # 무엇을 위한 서비스인지, 처음 기동 때 무엇이 만들어지는지 적는다.
  # ---------------------------------------------------------------------------
  db:
    image: postgres:18
    ports:
      - "5434:5432"    # 호스트 5434 → 컨테이너 5432 (로컬에 이미 있는 DB와 충돌 방지)
    env_file:
      - .env

volumes:
  db-data:
```
- 서비스마다 구분선 블록을 두고, 블록 첫 줄에 역할, 다음 줄에 왜 이렇게 했는지를 적습니다.
- 버전은 `latest` 대신 고정합니다.
- 비밀 값은 `.env`에 두고 compose에는 변수 이름만 씁니다.

## README
`lantern.yaml`의 `project.lifespan`에 따라 수준을 고릅니다.

**짧게 시험해 볼 프로젝트 (`short`)**
1. 제목과 한 줄 소개
2. 실행 방법 (필요한 것 · 명령)

**오래 운영할 프로젝트 (`long`)**
1. 가운데 정렬 머리: 제목 · 한 줄 소개 · 배지(플랫폼 · 언어 · 라이선스 · 릴리스)
2. 한 줄 인용으로 프로젝트의 성격
3. 왜 만들었나
4. 한눈에 보기 (그림이나 표 하나)
5. 특징 (기능마다 `###`와 짧은 설명)
6. 설치 (바로 쓰기 / 소스에서 빌드)
7. 사용법
8. 기여 방법 (자세한 것은 `CONTRIBUTING.md`)
9. 라이선스

- 절 제목에는 이모지를 하나씩만 씁니다. 본문에는 쓰지 않습니다.
- 경고와 주의는 `> ⚠️` 인용 블록으로 둡니다.

## LICENSE
저장소를 공개할 때만 정합니다. 이 표는 선택을 돕는 요약이며 법률 자문이 아닙니다.

| 분류 | 라이선스 | 특징 |
|---|---|---|
| 허용적 | MIT | 저작권 표시만 남기면 상업적 사용 · 수정 · 재배포가 자유롭다 |
| 허용적 | Apache-2.0 | MIT에 특허 사용 허락과 특허 소송 시 권리 종료 조항이 더해진다 |
| 허용적 | BSD-3-Clause | MIT와 비슷하고, 이름을 홍보에 쓰지 못하게 한다 |
| 약한 카피레프트 | MPL-2.0 | 고친 파일만 공개하면 된다 |
| 약한 카피레프트 | LGPL-3.0 | 라이브러리를 고친 부분만 공개하고, 가져다 쓰는 프로그램은 닫아 둘 수 있다 |
| 강한 카피레프트 | GPL-3.0 | 배포할 때 파생물 전체를 같은 라이선스로 공개해야 한다 |
| 강한 카피레프트 | AGPL-3.0 | GPL-3.0에 더해, 네트워크 서비스로 제공해도 소스를 공개해야 한다 |
| 소스 공개 (오픈소스 아님) | BSL · SSPL | 소스는 보이지만 상업적 사용 등을 제한한다 |
| 독점 | 없음 | LICENSE 대신 README에 "All rights reserved"를 적는다 |

**질문으로 고르기** — 위에서부터 차례로 묻습니다.
```text
1. 다른 사람이 고친 코드도 공개하게 하고 싶나요?
   ├─ 아니요 → 2. 특허 문제가 걱정되나요? (회사 · 특허가 얽힌 분야)
   │            ├─ 예     → Apache-2.0
   │            └─ 아니요 → MIT
   └─ 예     → 3. 서비스로만 제공해도(설치 파일을 나눠 주지 않아도) 공개하게 할까요?
                ├─ 예     → AGPL-3.0
                └─ 아니요 → GPL-3.0
4. (공개하게 하는 쪽을 골랐을 때) 공개하기 싫은 회사에는 돈을 받고 따로 쓰게 하고 싶나요?
   └─ 예 → 이중 라이선스 (아래)
```

**이중 라이선스** — 같은 코드를 두 조건으로 동시에 내는 방식입니다.
- 오픈소스(보통 AGPL-3.0)로는 무료로 쓰되 소스를 공개해야 하고, 소스를 공개하기 싫은 쪽은 유료 상용 라이선스를 삽니다.
- 공개 의무가 강할수록 상용 라이선스를 살 이유가 커져서, AGPL-3.0과 짝을 짓는 경우가 많습니다.
- **저작권자만 할 수 있습니다.** 외부 기여자가 있으면 그 코드의 저작권은 기여자에게 있으므로, 기여를 받기 전에 CLA(기여자 라이선스 동의)를 받아야 합니다.
- LICENSE에는 오픈소스 라이선스 전문을 두고, README에 상용 라이선스 문의 방법을 적습니다.

- LICENSE 파일에는 표준 전문을 그대로 쓰고, 연도와 저작권자만 채웁니다.
- 가져다 쓴 라이브러리의 라이선스와 맞는지 확인합니다 (예: GPL 라이브러리를 쓰면 MIT로 낼 수 없다).

## 폴더 구조
- **짧게 시험해 볼 프로젝트 (`short`):** 고른 기술의 기본 구조를 따릅니다.
- **오래 운영할 프로젝트 (`long`):** 고른 기술에 맞는 후보 2~3개를 사람에게 보여 주고 정합니다 (예: `backend/` · `frontend/` 분리, 기능별 폴더, 단일 앱). 정한 구조는 ADR과 시스템 구조 문서에 남깁니다.
- 새 최상위 폴더를 만들 때는 이유를 시스템 구조 문서에 한 줄로 남깁니다.
