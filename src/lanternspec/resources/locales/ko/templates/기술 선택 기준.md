# 📘 기술 선택 기준

> [!abstract] 한눈에 보기
> 프로젝트의 기술을 고를 때 쓰는 기준과 선택 순서입니다.
> `/l-init`은 의사결정 트리까지 사용합니다.
> 디자인 패턴처럼 기술이 정해진 뒤의 판단은 ADR을 쓸 때 이 기준을 참고합니다.
> 기준일: 2026-11-06

## 기준의 역할
- **필수:** 만족하지 못하면 후보에서 뺍니다.
- **요구 시 필수:** 프로젝트에 그 요구가 있을 때만 후보를 거릅니다.
- **비교:** 남은 후보를 견주는 데 씁니다.

| 표 | 필수 | 요구 시 필수 | 비교 |
|---|---|---|---|
| 공통 | 기능 적합성, 보안, 호환성 | 성능, 확장성 (목표 수치가 있을 때) | 개발 생산성, 비용, 유지보수성, 안정성, 생태계 성숙도, 배포 · 운영, 기술 지속 가능성 |
| 웹 | 브라우저 호환성 | 렌더링 방식, SEO, 접근성 | 초기 로딩 |
| 데스크톱 | OS 지원 | 시스템 API, 하드웨어 접근, 오프라인 기능, 로컬 보안 | 실행 성능, 시작 속도, 설치 크기, 네이티브 UX |
| 모바일 | 플랫폼 범위, 스토어 정책, OS 업데이트 | 네이티브 API, 백그라운드 실행, 오프라인 지원, 접근성 | 배터리 소비, 메모리 제약, UI 반응성, 앱 크기 |
| 서버 | 없음 | 인증 · 권한, 실시간 통신, API 방식, 백그라운드 작업 | 서버 확장성 |
| DB | 백업 · 복구 | 데이터 일관성, 데이터 모델 | 조회 방식, 데이터 확장, 구조 변경 |
| 인프라 | 없음 | 데이터 위치 | 인프라 비용, 배포 전략, 운영 방식, 자동 확장, 모니터링 · 로그, 장애 복구 |

기존 서비스(Supabase, Firebase 등)는 공통 기준에 데이터 모델, 데이터 일관성, 인프라 비용, 데이터 위치를 더해 판단합니다.

## 평가 기준

## 의사결정 트리
먼저 "쓰고 싶은 언어나 프레임워크가 있나요?"를 묻습니다. 있으면 그 기술을 쓰고, 정해지지 않은 영역만 아래를 따릅니다. 새 질문은 경로마다 이 질문을 포함해 3개까지입니다. 개발 환경(Docker) 질문은 따로 셉니다.

### 화면: 웹
"검색 결과에 잘 나와야 하나요?" (근거: SEO, 렌더링 방식)
- 예 — 쇼핑몰, 블로그, 서비스 소개 페이지처럼 처음 보는 사람이 검색으로 찾아오는 사이트 → Next.js
- 아니요 — 관리자 화면, 사내 도구처럼 가입한 사람만 들어와 쓰는 화면 → React + Vite

### 화면: 데스크톱
"프로그램에서 가장 중요한 것은 무엇인가요?" (근거: OS 지원, 개발 생산성, 실행 성능, 하드웨어 접근, 네이티브 UX)
- 여러 OS에서 쓸 프로그램을 빠르게 만들기 (추천) → Electron. 설치 크기와 메모리를 줄여야 하면 Tauri를 대안으로 보여 줍니다.
- 여러 OS에서 고성능이나 하드웨어 제어 → Qt
- Windows에 최적화 → .NET + WinUI 3
- macOS에 최적화 → SwiftUI

### 화면: 모바일
"앱에서 가장 중요한 것은 무엇인가요?" (근거: 플랫폼 범위, 개발 생산성, UI 반응성, 네이티브 API)
- iOS와 Android를 한 코드로 빠르게 만들기 (추천) → React Native + Expo
- iOS와 Android의 화면을 똑같이 맞추기 → Flutter
- iOS만 만들기 → SwiftUI
- Android만 만들기 → Kotlin + Jetpack Compose

### 화면을 여러 개 만들 때
- 웹과 데스크톱: 데스크톱 질문을 묻지 않고 Electron을 제안하며 Tauri를 대안으로 보여 줍니다. 웹 화면 코드를 함께 쓸 수 있습니다.
- 모바일과 다른 화면: 모바일 질문을 묻지 않고 React Native + Expo를 제안합니다. 화면 기술을 TypeScript로 맞출 수 있습니다.

### 서버와 DB
서버 질문의 답에 따라 나눕니다.

- 필요 없음: 서버를 정하지 않습니다. 데스크톱이나 모바일에서 데이터를 저장하면 SQLite를 제안합니다.
- 기존 서비스 활용: Supabase를 추천하고 Firebase를 대안으로 보여 줍니다. 모바일에서 오프라인 동작이 중요하면 Firebase를 권합니다.
- 직접 개발: "서버에서 가장 중요한 것은 무엇인가요?"를 묻습니다. (근거: 개발 생산성, 안정성, 서버 확장성, 유지보수성)
  - 빠르게 만들어 보기, 또는 AI · 데이터 처리 (추천) → FastAPI
  - 화면과 같은 언어로 개발하기 → NestJS (화면이 TypeScript일 때만 보여 줍니다)
  - 금융 · 공공처럼 안정성이 최우선 → Spring Boot
  - 많은 동시 접속 처리 → Go

직접 개발하면 DB는 묻지 않고 PostgreSQL을 제안하며 MySQL, SQLite를 대안으로 함께 보여 줍니다. (근거: 데이터 일관성, 데이터 모델)

직접 개발하면 개발 환경도 묻습니다: "개발 환경을 Docker로 맞출까요?" (근거: 배포 · 운영, 호환성)
- 예 — 컴퓨터마다 같은 DB · 서버로 실행해요 (팀이거나 DB 서버가 있으면 추천)
- 아니요 — 각자 설치해 실행해요

고른 결과는 기술 선택 ADR에 함께 남깁니다. Docker를 쓰면 compose 파일은 저장소 파일 규칙의 형식을 따릅니다.

## 대표 기술 비교
상태는 추천, 조건부, 추천 안 함 중 하나입니다. 더 이상 권하지 않는 기술은 행을 지우지 않고 상태를 바꿉니다.

| 기술 | 역할 | 언어 · 런타임 | 상태 | 장점 | 단점 | 검토 사항 |
|---|---|---|---|---|---|---|
| Next.js | 웹 화면 | TypeScript · Node.js | 추천 | CSR, SSR, SSG를 한 프레임워크에서 지원 | 렌더링과 캐싱 구조가 복잡 | SSR을 쓰면 Node.js 실행 환경이 필요 |
| React + Vite | 웹 화면 | TypeScript · Node.js | 추천 | 구조가 단순하고 정적 파일로 배포 가능 | 기본이 CSR이라 SEO에 불리 | 라우팅과 데이터 관리 도구를 따로 선택 |
| Electron | 데스크톱 화면 | TypeScript · Chromium + Node.js | 추천 | 웹 기술로 Windows, macOS, Linux를 지원하고 OS별 화면 차이가 적음 | Chromium을 포함해 설치 크기와 메모리 사용량이 큼 | 메이저 지원 기간이 짧아 잦은 업그레이드 필요, 코드 서명 |
| Tauri | 데스크톱 화면 | TypeScript + Rust · OS WebView | 조건부 | OS의 WebView를 써서 설치 크기가 작음 | OS별 WebView 차이를 시험해야 하고 네이티브 기능에 Rust가 필요할 수 있음 | Linux의 WebView 환경, 코드 서명 |
| Qt | 데스크톱 화면 | C++ · QML | 조건부 | 네이티브 성능과 하드웨어 접근, 여러 OS 지원 | 학습량이 많고 빌드와 배포가 복잡 | LGPL · GPL · 상용 라이선스 조건과 비용 |
| .NET + WinUI 3 | 데스크톱 화면 | C# · .NET | 조건부 | Windows 기능과 UX에 최적화, Visual Studio 도구 | Windows 전용 | 기존 자산이 WPF면 WPF도 검토 |
| SwiftUI | 데스크톱 화면, 모바일 화면 | Swift | 조건부 | macOS, iOS의 UX와 최신 기능에 최적화 | Apple 플랫폼 전용 | Mac과 Xcode 필요, Apple Developer Program 연 99 USD, App Store 밖 배포는 서명과 공증 조건 확인, Android를 나중에 만들면 코드 재사용 불가 |
| React Native + Expo | 모바일 화면 | TypeScript · React Native | 추천 | iOS와 Android를 한 코드로 개발, 웹 개발자가 접근하기 쉬움, React Native가 새 프로젝트에 프레임워크를 권장 | 특수한 네이티브 기능은 Swift나 Kotlin 코드가 필요할 수 있음 | 잦은 버전 업그레이드, 지원 OS 최소 버전 |
| Flutter | 모바일 화면 | Dart | 조건부 | 플랫폼 간 화면을 똑같이 맞추기 쉬움 | Dart를 새로 배워야 하고 OS 기본 UI와 차이가 생길 수 있음 | 앱 크기, 네이티브 플러그인 지원 |
