# 📘 할 일 나누기 기준

> [!abstract] 한눈에 보기
> 설계를 할 일로 나눌 때 따르는 기준입니다.
> `/l-task`는 이 기준으로 할 일의 크기를 정하고, 모르는 것을 둘 곳을 고릅니다.
> `/l-build`는 조사 할 일을 이 기준대로 처리합니다.
> 이 프로젝트에 맞지 않는 기준은 고쳐서 씁니다. AI는 고친 기준을 따릅니다.

## 크기
사람이 그 일에 손댈 시간을 모두 더한 값으로 정합니다. 쉬지 않고 이어서가 아니어도, 띄엄띄엄 한 시간을 더해 그 정도면 됩니다. AI가 실제로 쓴 시간이 아닙니다.
크기는 가장 가까운 칸을 고르는 눈금이지, 그 시간 안에 끝내겠다는 약속이 아닙니다.

| 크기 | 이런 일 | 예 |
|---|---|---|
| `${size.xs}` | 정해진 값 · 글자 · 설정 하나를 바꿉니다. 테스트를 새로 쓰지 않아도 됩니다 | 문구 수정, 환경 변수 추가, 링크 하나 더하기 |
| `${size.s}` | 파일 한두 개를 이미 정해진 방식대로 고칩니다. 새로 정할 것이 없습니다 | API 응답에 칸 하나 더하기, 입력 검사 함수 하나 |
| `${size.m}` | 여러 파일을 고치고 테스트를 새로 씁니다. 데이터 · API · 화면 중 한 층 안의 일입니다 | 가입 API, DB 연결과 첫 마이그레이션 |
| `${size.l}` | 데이터 · API · 화면 여러 층에 걸치거나, 처음 쓰는 기술 · 외부 서비스를 붙입니다 | 세션과 잠금 정책이 있는 로그인, 결제 연동 |

- **`${size.l}`을 넘을 것 같으면 나눕니다.** 그보다 큰 일은 검토하기 어렵고, 막혀도 늦게 알게 됩니다.
- **애매하면 큰 쪽으로 정합니다.** 작게 잡았다가 넘치는 것보다, 크게 잡았다가 일찍 끝나는 쪽이 계획을 덜 흔듭니다.

## 모르는 것을 어디에 두나
| 이런 모름 | 둘 곳 | 예 |
|---|---|---|
| 지금 작업과 상관없는 궁금증 | 아이디어 카드 (`/l-idea`) | "언젠가 GraphQL로 바꾸면 어떨까?" |
| 이 작업에 필요하고, 따져 보면 정할 수 있는 선택 | 설계에서 결정 (`/l-design` → ADR) | 세션과 JWT 중 무엇으로 로그인을 유지할까 |
| 이 작업에 필요하고, 직접 해 봐야 아는 것 | 조사 할 일 (아래 "조사 할 일") | 결제 서비스가 실제로 부분 환불을 지원하나, 이 라이브러리가 1만 건을 1초 안에 처리하나 |
| 사람만 답할 수 있는 것 | 해당 줄에 `❓ 확인 필요` | 환불은 며칠 안에만 되나 |

- **조사보다 결정이 먼저입니다.** 따져서 정할 수 있는 것을 조사 할 일로 미루지 않습니다.
- **추측으로 채우지 않습니다.** 사람만 답할 수 있는 것은 표시를 남기고, 그 할 일은 답이 올 때까지 시작하지 않습니다.

## 조사 할 일
직접 해 봐야 알 수 있는 것을 알아내는 할 일입니다. 결과물은 코드가 아니라 결론입니다.

```
- [ ] W-005-T01 [조사] 결제 서비스의 부분 환불 지원 확인 [크기:: ${size.s}] [기준:: AC-4]
- [ ] W-005-T02 환불 API [크기:: ${size.m}] [기준:: AC-4] [먼저:: T01]
```

- **크기는 시간 상한입니다.** 그 시간 안에 결론을 내지 못하면 멈추고 사람에게 묻습니다.
- **결론에 따라 달라지는 할 일은 조사 할 일 뒤에 둡니다** (`[먼저:: T01]`). 결론 없이 구현을 시작하지 않게 하기 위해서입니다.
- **결론은 이렇게 남깁니다.**
  - 무엇을 고를지 정해졌으면 ADR에 남기고, 확인한 근거(호출 결과, 시험 코드 위치)를 함께 적습니다.
  - 사실만 확인했으면 작업의 `기록.md`에 남깁니다.
- **시험 코드는 그대로 쓰지 않습니다.** 필요하면 구현 할 일에서 정식으로 다시 만듭니다.
